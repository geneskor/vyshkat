# ВышКат

Домашнее задание №1 по КПО.

Консольное приложение для учёта транспорта и инвентаря кикшеринга «ВышКат».

## Что делает программа

В программе можно добавлять транспорт и инвентарь, смотреть количество транспорта в парке, считать общее энергопотребление и получать список транспорта, который подходит новичкам.

Всё работает через консольное меню. Данные вводятся пользователем во время работы программы.

Реализованы три вида транспорта:

- `ElectricScooter` — электросамокат;
- `ElectricBike` — электровелосипед;
- `Bicycle` — велосипед.

Также есть три вида вещей:

- `Helmet` — шлем;
- `DockingStation` — док-станция;
- `ChargingCabinet` — зарядный шкаф.

Все объекты, которые ставятся на баланс, реализуют `InventoryItem`. У них есть название и инвентарный номер.

Объекты, которые потребляют электроэнергию, дополнительно реализуют `EnergyConsumer`.

## Запуск


## Работа с программой

После запуска появляется меню:

```text
========== ВЫШКАТ ==========
1. Добавить транспорт
2. Добавить инвентарь
3. Показать количество транспорта
4. Показать суммарное энергопотребление
5. Показать транспорт для новичков
6. Показать весь инвентарь
0. Выход
```

При добавлении транспорта нужно выбрать его тип, ввести название, инвентарный номер и удобство для новичков от 1 до 10.

Для электрического транспорта дополнительно вводится суточное энергопотребление.

Перед добавлением транспорт проходит проверку сервисным центром. Если проверка не пройдена, транспорт не добавляется в парк.

Для новичков подходит транспорт с `beginnerEase >= 6`.

После выполнения команды программа снова показывает меню. Для выхода нужно ввести `0`.

## Структура проекта

Код разделён на несколько частей.

### domain

Здесь находятся классы транспорта и вещей, а также интерфейсы `InventoryItem`, `EnergyConsumer` и `ServiceCenter`.

`Transport` — базовый класс для транспорта, `Thing` — для вещей.

### service

Здесь находятся два сервиса:

- `FleetService` — добавляет транспорт после техосмотра, считает его количество и возвращает список транспорта для новичков;
- `InventoryService` — хранит инвентарь и считает суммарное суточное энергопотребление.

### config

Здесь находится `AppModule`, в котором настраивается Google Guice.

### ConsoleApplication и Main

`ConsoleApplication` отвечает за консольное меню, ввод данных и вывод результатов.

В `Main` создаётся Guice-контейнер, получаются сервисы и запускается приложение.

Таким образом, работа с консолью отделена от логики учёта транспорта и инвентаря.

## SOLID

Наиболее заметен в проекте принцип Dependency Inversion.

`FleetService` работает с интерфейсом `ServiceCenter`, а не создаёт конкретный `DefaultServiceCenter` самостоятельно.

Зависимость передаётся через конструктор:

```java
public FleetService(ServiceCenter serviceCenter, InventoryService inventoryService)
```

А в `AppModule` указывается реализация:

```java
bind(ServiceCenter.class).to(DefaultServiceCenter.class);
```

За счёт этого можно заменить реализацию техосмотра, не меняя `FleetService`.

Например, в тестах используется:

```java
ServiceCenter serviceCenter = transport -> true;
```

Или:

```java
ServiceCenter serviceCenter = transport -> false;
```

Также разделены `InventoryItem` и `EnergyConsumer`, поскольку не каждый инвентарный объект должен потреблять электроэнергию.

### Какой принцип применён не полностью

В `InventoryService` объединены хранение инвентаря и расчёт энергопотребления.

С точки зрения SRP эти задачи можно было бы разделить по разным классам, но так как приложение неболльшоее, обе операции оставлены в одном сервисе.

## Расширение проекта

Если понадобится добавить новый вид транспорта, можно создать класс, наследующий `Transport`.

Если он потребляет электроэнергию, нужно также реализовать `EnergyConsumer`.

При этом менять `FleetService` не потребуется. Но для добавления нового типа в консольное меню нужно будет дополнить `ConsoleApplication`.

Если понадобится учитывать сотрудников, для них можно сделать отдельный класс. Реализовывать `InventoryItem` он не должен, поскольку сотрудники не находятся на балансе.

Если появится склад запчастей, можно добавить отдельные классы для запчастей и сервис для работы со складом.

## DI

Для внедрения зависимостей используется Google Guice.

В `AppModule` настраиваются зависимости, а в `Main` создаётся контейнер.

`InventoryService` зарегистрирован как singleton, чтобы `Main` и `FleetService` использовали один и тот же список инвентаря.

`ConsoleApplication` получает сервисы, `Scanner` и `PrintStream` через конструктор.

Это также позволяет тестировать консольный ввод и вывод без ручного запуска программы.

## Тесты

Тесты написаны на JUnit 5.

В проекте есть:

- `FleetServiceTest` — проверка приёмки транспорта, отказа сервисного центра, количества транспорта и правила для новичков;
- `InventoryServiceTest` — проверка хранения инвентаря и подсчёта энергопотребления;
- `DomainModelTest` — проверка основных свойств доменных классов;
- `MainTest` — проверка работы консольного меню.

В `FleetServiceTest` используется подмена `ServiceCenter` через конструктор. Это позволяет отдельно проверить, что происходит при успешном и неуспешном техосмотре.

Также проверяется граничное значение `beginnerEase = 6`.

В `MainTest` пользовательский ввод имитируется через `Scanner`, а вывод записывается в `ByteArrayOutputStream`.

Это позволяет проверить работу меню автоматически.
